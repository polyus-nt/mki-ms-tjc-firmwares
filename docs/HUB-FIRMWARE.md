# Центральный хаб МС-ТЮК: аппаратный API v2

`firmware/hub/sketch.cpp` — актуальная рукописная прошивка центральной платы.
GraphML не участвует в сборке и не изменяется. `firmware/hub/Hub.h` — независимый
от STM32 автомат; `tests/hub_test.cpp` проверяет его на компьютере.

## Реальная топология

### Две Arduino актуаторов

Компьютер продолжает использовать **виртуальный node 14 и глобальный idx 0..5**.
Для GET_PWM/GET_RPM/SET_PWM хаб отправляет idx 0..3 шлюзу 14 без изменений,
idx 4..5 — шлюзу 17 с локальным idx 0..1. Ответ компьютеру восстанавливает
исходные node/idx/session_id/tx_id. Прямые запросы компьютера на node 17 отклоняются
INVALID_NODE: нельзя обойти единый API и координацию тестовых неисправностей.

GET_MODE (idx=255) читает обе Arduino, возвращает mode/global idx (mode=0: idx=255).
Если одновременно активны два сценария, возвращает INTERNAL_ERROR, а не скрывает
конфликт. SET_MODE сначала читает обе платы. Повтор текущего mode/idx идемпотентен:
не меняет PWM и не перезапускает 30-секундный таймер. Для смены сценария хаб
последовательно подтверждает mode=0 на обеих платах и только затем включает
выбранный mode/idx. Ошибка, неверный ответ или таймаут останавливают последовательность;
после неподтверждённого сброса новый сценарий НЕ включается. Сброс не восстанавливает
старый PWM. Каждый внутренний шаг получает отдельный session_id, ответ наружу —
исходный session_id. Общий дедлайн режима 4 с; обычного запроса — 3 с.
Стандартный host timeout 5 с включает передачу запросов и ответов компьютера.

Обе Arduino должны быть доступны для GET_MODE/SET_MODE; PWM/RPM доступной платы
работают независимо от второй. Хаб не кеширует режим и не повторяет изменяющие
команды после таймаута. Перезапуск хаба не выключает текущий сценарий Arduino;
следующая команда режима заново читает обе платы. Существующий конфликт устраняется
следующим успешным SET_MODE, прошедшим оба подтверждённых сброса.

Сборка нового шлюза: `py -3 scripts/build.py --target gateway-actuator-2`.
Файл: `build/gateways/actuator-2/sketch.bin`, SimpleBus-адрес 17 (`11` HEX).

Проверен runtime `tjc-ms1-main-a4/1.0` из `kruzhok-team/lapki-compiler`, ревизия
`c0e235f364f21b1a7ba8dbb598ef0bc983511af6`. Он предоставляет **один USART1**:
PB6/PB7, AF0; управление RS485 ReDe — PA0. Компьютер и шлюзы используют общую
полудуплексную SimpleBus. Отдельного UART компьютера эта прошивка не выдумывает.
Соответствие реальному адаптеру компьютера и ревизии стенда ещё нужно проверить.

| Получатель | Адрес, decimal | ASCII HEX |
| --- | ---: | --- |
| Центральный хаб | 12 | `0C` |
| Шлюз датчиков | 13 | `0D` |
| Шлюз актуаторов | 14 | `0E` |
| Кнопочница, концевики | 15 | `0F` |
| Обычная лампочница, замки и пылесос | 16 | `10` |
| Второй шлюз актуаторов | 17 | `11` |
| Компьютер | 99 | `63` |

UART: 115200, 8N1. Один байт прикладного кадра передаётся пятибайтовым пакетом
`CR, addr_hi_ASCII, addr_lo_ASCII, data, LF`. Данные могут содержать CR/LF:
позиция четвёртого байта фиксирована, экранирование не требуется. В пакетах нет
адреса отправителя. Запросы PC и ответы шлюзов приходят на `0C`; их различаем
по `kind` только после сборки и проверки полного 28-байтового кадра и CRC.

## Работа автомата

1. Хаб/PC согласуют READY → CLAIM → GRANT, затем PC отправляет полный запрос v2 на `0C`.
2. Хаб проверяет version/kind/status, команду, node, индекс и payload через общий
   `validateRequest`. Некорректный запрос получает стандартную ошибку; мусор/CRC
   ошибка не имеют достоверных реквизитов и отбрасываются.
3. Корректный кадр маршрутизируется на шлюз/плату 13..17. Для вентиляторов
   глобальный индекс преобразуется в локальный, как описано выше.
4. Хаб ждёт ответ того же version/kind/session_id/tx_id/node/command/idx. Неизвестный статус,
   зарезервированный REQUEST_ID_CONFLICT и ненулевой payload ошибки отбрасываются.
5. Ответ с восстановленными реквизитами исходного запроса передаётся PC на `63`.

В один момент есть одна глобальная транзакция. Пакеты отправляются по одному,
без искусственных межпакетных пауз. Между ними обслуживается приём и таймеры.
`sendPacket` ждёт завершения UART TC одного пакета (~0,434 мс).
Хаб не запускает периодическую телеметрию и не принимает решений о PWM.

Параллельный запрос сохраняет один отложенный BUSY, который отправляется целым
кадром после основного ответа. Ещё более поздние запросы отбрасываются: память
ограничена, кадры не перемешиваются. PC должен сериализовать запросы своей очередью;
BUSY не устраняет физическую коллизию, если PC нарушает полудуплексный обмен.

Адрес восьмилампочницы неизвестен; замки и пылесос **не маршрутизируются**.

`get_door_state` (`0x22`) относится к node 15, idx 0..1: хаб пересылает его
не Arduino, а [кнопочнице](BUTTONS-FIRMWARE.md), которая сама использует Button.
Старый маршрут этой команды через node 13 теперь получает `INVALID_NODE`.
`set_door_lock` пока получает UNKNOWN_COMMAND. Arduino не назначается владельцем
этих выходов. Семантика датчиков/PWM/режимов остаётся в соответствующих Arduino.

## Тайм-ауты и восстановление

Полная транзакция хаба: 3000 мс (GET_MODE/SET_MODE: 4000 мс) от принятия проверенного запроса, включая пересылку
шлюзу. Шлюз: 1500 мс; рекомендуемый PC deadline: 5000 мс. Частичный кадр сбрасывается
через 250 мс между байтами либо 1000 мс общей длительности. Ошибка транзакции:
DEVICE_TIMEOUT; переполнение runtime FIFO: TRANSPORT_OVERFLOW. Ошибки содержат
исходные реквизиты и нулевые 8 байтов payload. Автоматического повтора нет.

При старте и после отправки ошибки вход дренируется до 250 мс тишины, но не дольше
1000 мс: шумящий узел не может навсегда оставить хаб в Recovering. На пределе
парсер сбрасывается и хаб снова принимает запросы; поздние ответы без активного
совпадающего запроса игнорируются. Это ограничение восстановления **не является
доказательством отсутствия поздних байтов**. PC после своего тайм-аута должен
восстановить транспорт, а не сразу повторять изменяющую команду.

v2 содержит 64-битную session_id: Arduino копирует её в ответ, хаб и шлюз
проверяют вместе с tx_id. Сервер начинает с случайной ненулевой сессии и
при переполнении двухбайтового tx_id увеличивает сессию, продолжая с tx_id=1.
Общее число запросов не ограничивается 65535. Совпадение случайной сессии
между процессами крайне маловероятно, но session_id не является аутентификацией.
Тайм-аут установки PWM означает неизвестный исход, а не гарантированное отсутствие
физического воздействия. Непрерывный шум может портить реальные кадры даже после
выхода из Recovering: исправить неисправную шину программной гарантией нельзя.

## Сборка и проверки

### Минимальная тестовая прошивка SimpleBus

`firmware/hub-test/sketch.cpp` использует тот же runtime main-a4, но **не содержит
аппаратного API, CRC, маршрутизации и опроса шлюзов**. На любой полезный байт
корректного пакета SimpleBus, адресованного 12, возвращает `0xAA` на адрес 99.
Одиночные UART-байты вне пакета SimpleBus не являются запросами этого теста.
Светодиод №1 (`LED(1)`, физический PA5 по upstream `LED.h`) включается при старте
и затем мигает независимо от обмена. Используется сам класс LED из main-a4,
а не отдельная реализация GPIO. Переключения выполняются по `millis()`, без
блокирующего `LED::blink()`: ожидание следующего переключения не задерживает приём.
LED №2 (PA6) загорается после первого принятого UART-байта, **до** проверки
обрамления и адреса SimpleBus и остаётся включённым до перезапуска.
LED №3 (PA7) включается на каждый корректный пакет SimpleBus на адрес 12,
**до** отправки ответа. Перед отправкой есть диагностическая пауза `delay(100)`,
чтобы вспышку было видно; после возврата `sendPacket()` LED №3 выключается.
На старте LED №2 и №3 выключены. Активность других участников/шум тоже может включить LED №2;
для чистой проверки перезапустите плату перед запросом и остановите другой обмен.

При запросе из `hub_test_console.py`:

- LED №2 и №3 не включились: не зафиксирован UART RX, проверяйте входной тракт.
- LED №2 включился, №3 не вспыхивал: UART получил байты, но не принял пакет на адрес 12
  (например, обрамление/адрес/скорость, испорченные или чужие пакеты).
- LED №3 вспыхнул и остался гореть: пакет принят, но выполнение не прошло
  до конца отправки (возможное зависание внутри `sendPacket()`).
- LED №3 вспыхнул и погас, но RX компьютера пуст: `sendPacket()` завершился,
  UART подтвердил TC и драйвер переключён на приём; проверяйте обратный тракт.
  Завершение функции не доказывает физическое получение ответа компьютером.

Счётчик RX добавляется только в сгенерированную `build/hub-test/platform/UART.hpp`.
Наблюдение проверяет RXNE перед чтением RDR, не использует общий debug-флаг,
который upstream выставляет и при передаче. Исходный UART и рабочие сборки не меняются.

На Windows:

```powershell
py -3 scripts/build.py --target hub-test
```

Результат — `build/hub-test/sketch.bin`. Прошейте **только центральную плату**
тем же способом, которым загружаете обычный usercode main-a4 (адрес `0x08003800`,
не начало flash `0x08000000`; загрузчик не стирать). Сборка сама ничего не прошивает.
На время теста остановите commutator и остальные инициаторы обмена на шине.

```powershell
py -3 scripts/hub_test_console.py COM13
```

Введите `42`, `0`, `0xFF` или любой другой байт 0..255. Каждый запрос — ровно один
пакет, без API v2. Для `42` ожидается:

```text
TX RAW: 0D 30 43 2A 0A
RX RAW: 0D 36 33 AA 0A
HUB_OK: 170 (0xAA)
```

Разбиение RX на строки может отличаться. Эхо запроса игнорируется при поиске ответа,
но выводится в сыром журнале. Отправляйте следующий запрос только после ответа или
тайм-аута. Это не проверка датчиков и не рабочая прошивка системы.

Обычная сборка `--target all` этот тест **не включает**. После проверки верните
на хаб `build/hub/sketch.bin`, иначе обычный API работать не будет.
Для Linux/macOS замените `py -3` на `python3`, укажите свой serial-порт.
Альтернативная сборка: `make build-hub-test` или `scripts/build_hub.py --test-echo`.

### Рабочая прошивка API

```sh
python3 scripts/build_hub.py
g++ -std=c++11 -Wall -Wextra -Werror -fsanitize=address,undefined -g \
  tests/hub_test.cpp -o /tmp/tjc-hub-test
ASAN_OPTIONS=detect_leaks=0 /tmp/tjc-hub-test
```

Для ARM tools вне PATH: `--toolchain-bin /path/to/bin`.
Runtime находится в `firmware/runtime`: отдельный lapki-compiler не нужен.
На Windows запускайте `py -3 scripts/build_hub.py`.
`--prepare-only` проверяет runtime без компиляции. Проверяются SHA-256
исходников после нормализации CRLF в LF;
готовится локальная копия с теми же исправлениями SimpleBus, что и у шлюзов:
64-ячейковая FIFO, overflow, безопасные короткие IRQ-секции и побайтный сдвиг
без невыравненных halfword-доступов. Upstream не изменяется, зависимостей скрипт
не скачивает. QHSM не нужен.

Артефакты: `build/hub/sketch.{elf,bin,map}`. Cortex-M0+, STM32G030x6. Векторы
подтверждены по `0x08003800`, ровно по одному USART1/SysTick обработчику.
GCC 14.3.1: text 9632, data 20, bss 2240 байтов (bss включает зарезервированные
линкером heap/stack; фактическая `.bss` 700 байтов). Остаются upstream nosys/RWX
предупреждения linker script. BIN — usercode, не bootloader; устройство не прошито.

Проверены датчики/актуаторы, сохранение кадра и applied PWM, все поля корреляции,
ошибки CRC/индексов/node, неполный кадр, BUSY без роста очереди, тайм-аут при
пересылке/ожидании, поздний ответ, overflow, ограниченный noisy recovery и millis
wrap. Native/сборка не заменяют проверку UART, RS485 и всей цепочки на стенде.

## Кнопочное открытие дверей

Хаб опрашивает счётчики кнопок 3/4 на узле 15 между внешними запросами
и передаёт команду открытия 0x44 на обычную lmp (16). Локальный таймер закрывает
выход через 2 секунды без компьютера. На старте замки заблокированы.
Концевики idx=0/1 остаются на физических пинах кнопочницы 1/2.
Описание [автономного управления](DOOR-CONTROL.md) включает
новые внутренние команды 0x27/0x44, приоритеты и стендовую проверку.

Актуальное согласование PC с хабом, миграция и ограничения: [FAST-SIMPLEBUS.md](FAST-SIMPLEBUS.md).
