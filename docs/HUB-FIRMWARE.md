# Центральный хаб МС-ТЮК: аппаратный API v2

`firmware/hub/sketch.cpp` — актуальная рукописная прошивка центральной платы.
GraphML не участвует в сборке и не изменяется. `firmware/hub/Hub.h` — независимый
от STM32 автомат; `tests/hub_test.cpp` проверяет его на компьютере.

## Реальная топология

Проверен runtime `tjc-ms1-main-a4/1.0` из `kruzhok-team/lapki-compiler`, ревизия
`c0e235f364f21b1a7ba8dbb598ef0bc983511af6`. Он предоставляет **один USART1**:
PB6/PB7, AF0; управление RS485 ReDe — PA0. Компьютер и шлюзы используют общую
полудуплексную SimpleBus. Отдельного UART компьютера эта прошивка не выдумывает.
Соответствие реальному адаптеру компьютера и ревизии стенда ещё нужно проверить.

| Получатель | Адрес, decimal | ASCII HEX |
| --- | ---: | --- |
| Центральный хаб | 12 | `0C` |
| Шлюз датчиков | 13 | `0D` |
| Шлюз актуаторов | 14 | `0E` |
| Компьютер | 99 | `63` |

UART: 9600, 8N1. Один байт прикладного кадра передаётся пятибайтовым пакетом
`CR, addr_hi_ASCII, addr_lo_ASCII, data, LF`. Данные могут содержать CR/LF:
позиция четвёртого байта фиксирована, экранирование не требуется. В пакетах нет
адреса отправителя. Запросы PC и ответы шлюзов приходят на `0C`; их различаем
по `kind` только после сборки и проверки полного 28-байтового кадра и CRC.

## Работа автомата

1. PC отправляет полный запрос v2, addressed `0C`.
2. Хаб проверяет version/kind/status, команду, node, индекс и payload через общий
   `validateRequest`. Некорректный запрос получает стандартную ошибку; мусор/CRC
   ошибка не имеют достоверных реквизитов и отбрасываются.
3. Корректный кадр без изменений пересылается на `0D` или `0E`.
4. Хаб ждёт ответ того же version/kind/session_id/tx_id/node/command/idx. Неизвестный статус,
   зарезервированный REQUEST_ID_CONFLICT и ненулевой payload ошибки отбрасываются.
5. Ответ без изменений передаётся PC на `63`.

В один момент есть одна глобальная транзакция. Пакеты отправляются по одному,
не менее 2 мс между завершением предыдущего и началом следующего. Между ними
обслуживается приём и таймеры. `sendPacket` синхронен лишь на один пакет (~5.21 мс).
Хаб не запускает периодическую телеметрию и не принимает решений о PWM.

Параллельный запрос сохраняет один отложенный BUSY, который отправляется целым
кадром после основного ответа. Ещё более поздние запросы отбрасываются: память
ограничена, кадры не перемешиваются. PC должен сериализовать запросы своей очередью;
BUSY не устраняет физическую коллизию, если PC нарушает полудуплексный обмен.

Адрес восьмилампочницы неизвестен; замки и пылесос **не маршрутизируются**.
`set_door_lock` пока получает UNKNOWN_COMMAND. Arduino не назначается владельцем
этих выходов. Семантика датчиков/PWM/режимов остаётся в соответствующих Arduino.

## Тайм-ауты и восстановление

Полная транзакция хаба: 3000 мс от принятия проверенного запроса, включая пересылку
шлюзу. Шлюз: 1500 мс; рекомендуемый PC deadline: 5000 мс. Частичный кадр сбрасывается
через 250 мс между байтами либо 1000 мс общей длительности. Ошибка транзакции:
DEVICE_TIMEOUT; переполнение runtime FIFO: TRANSPORT_OVERFLOW. Ошибки содержат
исходные реквизиты и нулевые 8 байтов payload. Автоматического повтора нет.

При старте и после отправки ошибки вход дренируется до 250 мс тишины, но не дольше
1000 мс: шумящий узел не может навсегда оставить хаб в Recovering. На пределе
парсер сбрасывается и хаб снова принимает запросы; поздние ответы без активного
совпадающего запроса игнорируются. Это ограничение восстановления **не является
доказательством отсутствия поздних байтов**. PC после своего тайм-аута должен
восстановить транспорт, а не сразу повторять изменяющую команду.

v2 содержит 64-битную session_id: Arduino копирует её в ответ, хаб и шлюз
проверяют вместе с tx_id. Сервер начинает с случайной ненулевой сессии и
при переполнении двухбайтового tx_id увеличивает сессию, продолжая с tx_id=1.
Общее число запросов не ограничивается 65535. Совпадение случайной сессии
между процессами крайне маловероятно, но session_id не является аутентификацией.
Тайм-аут установки PWM означает неизвестный исход, а не гарантированное отсутствие
физического воздействия. Непрерывный шум может портить реальные кадры даже после
выхода из Recovering: исправить неисправную шину программной гарантией нельзя.

## Сборка и проверки

```sh
python3 scripts/build_hub.py --compiler-root /path/to/lapki-compiler
g++ -std=c++11 -Wall -Wextra -Werror -fsanitize=address,undefined -g \
  tests/hub_test.cpp -o /tmp/tjc-hub-test
ASAN_OPTIONS=detect_leaks=0 /tmp/tjc-hub-test
```

Для ARM tools вне PATH: `--toolchain-bin /path/to/bin`. `--prepare-only` проверяет
runtime без компиляции. Проверяются SHA-256 всех используемых upstream файлов;
готовится локальная копия с теми же исправлениями SimpleBus, что и у шлюзов:
64-ячейковая FIFO, overflow, безопасные короткие IRQ-секции и побайтный сдвиг
без невыравненных halfword-доступов. Upstream не изменяется, зависимостей скрипт
не скачивает. QHSM не нужен.

Артефакты: `build/hub/sketch.{elf,bin,map}`. Cortex-M0+, STM32G030x6. Векторы
подтверждены по `0x08003800`, ровно по одному USART1/SysTick обработчику.
GCC 14.3.1: text 9632, data 20, bss 2240 байтов (bss включает зарезервированные
линкером heap/stack; фактическая `.bss` 700 байтов). Остаются upstream nosys/RWX
предупреждения linker script. BIN — usercode, не bootloader; устройство не прошито.

Проверены датчики/актуаторы, сохранение кадра и applied PWM, все поля корреляции,
ошибки CRC/индексов/node, неполный кадр, BUSY без роста очереди, тайм-аут при
пересылке/ожидании, поздний ответ, overflow, ограниченный noisy recovery и millis
wrap. Native/сборка не заменяют проверку UART, RS485 и всей цепочки на стенде.
