# Протокол управления охлаждением

## Общие правила

- Один вызов `sendPacket` переносит один непрозрачный байт.
- Команда определяет точное число следующих байтов; длина внутри сообщения не передаётся.
- Значение байта данных никогда не интерпретируется как разделитель.
- Многобайтные целые передаются старшим байтом вперёд.
- Температура кодируется парой `int8 whole`, `uint8 fraction`; дробь `0..255` соответствует `0..99` сотых градуса.
- RPM передаётся непосредственно как `uint16`, без нормализации.
- Успешный ответ завершается `OK=0x03`. Ошибка состоит из одного статусного байта.
- Получатель прекращает неполный обмен по тайм-ауту 2 секунды и возвращается к ожиданию команды.

## Адреса SimpleBus

| Узел | Адрес |
| --- | ---: |
| Центральная TJC-плата | `12` |
| TJC-плата датчиков | `13` |
| TJC-плата актуаторов | `14` |
| ПК | `99` |

## Статусы

| Код | Имя | Значение |
| ---: | --- | --- |
| `0x03` | `OK` | Команда выполнена, все предшествующие поля ответа валидны |
| `0xE0` | `INVALID_ARGUMENT` | Поле вне диапазона или недопустимая комбинация |
| `0xE1` | `VERSION_CONFLICT` | Ожидаемая версия не совпала |
| `0xE2` | `DENIED` | Команда запрещена текущим safety-режимом |
| `0xE3` | `BUSY` | Уже действует несовместимая операция или cooldown |

## Arduino датчиков

### `POLL_SENSORS = 0x01`

Обновляет неблокирующие измерения. Ответ: `OK`.

### `READ_SENSORS = 0x04`

Ответ содержит 10 байтов:

| Позиция | Поле |
| ---: | --- |
| 0 | Hall: `0` или `1` |
| 1 | Концевик 1: `0` или `1` |
| 2 | Концевик 2: `0` или `1` |
| 3 | Концевик 3: `0` или `1` |
| 4 | Внутренняя температура, whole |
| 5 | Внутренняя температура, fraction |
| 6 | Наружная температура, whole |
| 7 | Наружная температура, fraction |
| 8 | Флаги датчиков |
| 9 | `OK` |

Флаги: bit 0 — inside valid, bit 1 — inside fresh, bit 2 — outside valid, bit 3 — outside fresh. Остальные биты равны нулю.

## Arduino актуаторов

| Код | Команда | Поля запроса |
| ---: | --- | --- |
| `0x01` | `GET_ACTUATOR_STATE` | нет |
| `0x06` | `UPDATE_ENVIRONMENT` | inside whole, inside fraction, sensor flags, door open, door stage |
| `0x08` | `SET_TARGET` | target `0..60` |
| `0x09` | `PROPOSE_PID` | expected version u16, kp u16, ki u16, kd u16 |
| `0x0A` | `PROPOSE_WEIGHTS` | expected version u16, weight 1..4 u8 |
| `0x0B` | `CONFIRM_CONFIG` | candidate version u16 |
| `0x0C` | `ROLLBACK_CONFIG` | candidate version u16 |
| `0x0D` | `SET_DOOR_POLICY` | expected version u16, policy u8, limited PWM u8 |
| `0x0E` | `PROBE_FAN` | fan index `0..3` |
| `0x0F` | `CLEAR_EMERGENCY` | нет |
| `0x10` | `GET_CONTROL_CONFIG` | нет |

Коэффициенты PID — беззнаковые fixed-point значения с масштабом 1000. Например, `1.250` передаётся как `1250`. Кандидатная версия равна `0xFFFF`, если кандидата нет.

Ответ `GET_ACTUATOR_STATE` содержит 21 байт:

| Позиции | Поле |
| --- | --- |
| 0 | target |
| 1 | mode |
| 2 | door policy |
| 3–4 | stable config version |
| 5–6 | candidate config version или `0xFFFF` |
| 7–10 | применённый PWM fan 1..4 |
| 11–18 | RPM fan 1..4, четыре u16 |
| 19 | failed fan mask, bit 0..3 |
| 20 | `OK` |

Ответ `GET_CONTROL_CONFIG` содержит 18 байтов: stable version u16, candidate version u16, kp u16, ki u16, kd u16, четыре веса u8, door policy u8, limited PWM u8, target u8, `OK`.

Изменяющие команды отвечают одним статусом. `PROPOSE_PID` допускает изменение только одного коэффициента не более чем на 10 процентов от стабильного значения. `PROPOSE_WEIGHTS` и `PROPOSE_PID` создают десятиминутного кандидата. `CONFIRM_CONFIG` сохраняет кандидата как стабильный. `ROLLBACK_CONFIG` или истечение окна восстанавливает стабильную конфигурацию.

## Сквозной обмен управления ПК ↔ центральная TJC ↔ TJC актуаторов

Этот обмен существует только для управляющих команд Arduino актуаторов. Он
позиционный и последовательный: центральная TJC принимает один запрос от ПК,
передаёт его TJC актуаторов, ждёт полный фиксированный ответ и только затем
берёт следующий запрос или посылает периодическую телеметрию. В один момент
времени может быть только один такой обмен.

### Внешняя обёртка на линии ПК—центральная TJC

ПК посылает на адрес `12` байт `CONTROL_REQUEST=0x11`, затем байт кода команды
и ровно столько payload-байтов, сколько указано ниже. Центральная TJC
пересылает **только** код и payload на адрес `14`; Arduino получает ровно тот
же поток. После полного ответа Arduino центральная TJC посылает на адрес `99`
байт `CONTROL_RESPONSE=0x12`, исходный код команды и ровно фиксированное тело
ответа. Код команды во внешнем ответе нужен для проверки ожидаемого типа, а не
для корреляции нескольких одновременных запросов: их протокол запрещает.

| Команда | Payload запроса | Всего байтов запроса после `0x11` | Тело успешного ответа Arduino | Всего байтов после `0x12` в ответе ПК |
| --- | ---: | ---: | ---: | ---: |
| `GET_ACTUATOR_STATE` | 0 | 1 | 21 | 22 |
| `UPDATE_ENVIRONMENT` | 5 | 6 | 1 | 2 |
| `SET_TARGET` | 1 | 2 | 1 | 2 |
| `PROPOSE_PID` | 8 | 9 | 1 | 2 |
| `PROPOSE_WEIGHTS` | 6 | 7 | 1 | 2 |
| `CONFIRM_CONFIG` | 2 | 3 | 1 | 2 |
| `ROLLBACK_CONFIG` | 2 | 3 | 1 | 2 |
| `SET_DOOR_POLICY` | 4 | 5 | 1 | 2 |
| `PROBE_FAN` | 1 | 2 | 1 | 2 |
| `CLEAR_EMERGENCY` | 0 | 1 | 1 | 2 |
| `GET_CONTROL_CONFIG` | 0 | 1 | 18 | 19 |

Для меняющих команд тело ответа — ровно один из `OK`, `INVALID_ARGUMENT`,
`VERSION_CONFLICT`, `DENIED` или `BUSY`. Для двух команд чтения это полный
позиционный ответ из предыдущего раздела, в том числе финальный `OK`. Байт
`0x03` внутри RPM или любого другого позиционного поля не является окончанием
ответа: центральная TJC ожидает все 21 или 18 байтов соответственно.

`UPDATE_ENVIRONMENT` — внутренний транспортный запрос: центральная TJC
создаёт и посылает его актуатору каждые 2 секунды, используя последнюю пару
температуры и флаги. Он не требует отдельной команды ПК и не заменяет
периодическую телеметрию.

### Тайм-аут и восстановление

- После `CONTROL_REQUEST` центральная TJC ждёт каждый недостающий байт ровно
  до 2 секунд. Неполный запрос отбрасывается, автомат возвращается в idle.
- После пересылки в TJC актуаторов тот же 2-секундный лимит действует на
  полный ответ Arduino. Пока он не завершён, центральная TJC не посылает
  телеметрию и не принимает новый управляющий запрос.
- При обрыве ответа центральная TJC не подделывает `OK` или иной статус. Она
  через 2 секунды возвращается в idle; ПК отмечает запрос как `timeout` по
  собственному 2-секундному ожиданию и может послать следующую команду.
- Периодическая 29-байтовая телеметрия не интерливится ни с запросом, ни с
  `CONTROL_RESPONSE`; после timeout или полного ответа она возобновляется с
  очередного полного кадра.

### Тестовые векторы сквозного обмена

Ниже `→12` означает байты от ПК центральной TJC, `→14` — пересылку на TJC
актуаторов, `→99` — ответ ПК. Во всех строках `→14` повторяет команду и payload
из `→12` без первого байта `0x11`.

| Команда | `→12` | `→99` (успешный пример) |
| --- | --- | --- |
| state | `11 01` | `12 01 19 00 00 00 02 FF FF 80 80 80 80 03 03 0F A0 17 70 FF FF 00 03` |
| environment | `11 06 19 00 03 00 01` | `12 06 03` |
| target | `11 08 1E` | `12 08 03` |
| PID | `11 09 00 02 00 DC 00 0B 00 00` | `12 09 03` |
| weights | `11 0A 00 02 04 03 02 01` | `12 0A 03` |
| confirm | `11 0B 00 03` | `12 0B 03` |
| rollback | `11 0C 00 03` | `12 0C 03` |
| door policy | `11 0D 00 02 01 80` | `12 0D 03` |
| probe | `11 0E 02` | `12 0E 03` |
| clear emergency | `11 0F` | `12 0F 03` |
| config | `11 10` | `12 10 00 02 FF FF 00 C8 00 0A 00 00 01 01 01 01 00 80 19 03` |

Ошибочный пример конфликта версии: `→12: 11 0A 00 01 01 01 01 01`,
`→99: 12 0A E1`. Неполный `11 09 00 02` не имеет ответа; через 2 секунды он
отбрасывается, после чего `11 0F` снова корректно даёт `12 0F 03`.

## Телеметрия для ПК

Центральная TJC-плата отправляет на адрес `99` стартовый байт `0x0C`, затем ровно 29 байтов payload и завершающий `0x0C`. Внутреннее значение `0x0C` является данными по позиции.

| Позиции | Поле |
| --- | --- |
| 0 | версия формата: `1` |
| 1 | Hall |
| 2–3 | внутренняя температура |
| 4–5 | наружная температура |
| 6 | флаги датчиков |
| 7 | target |
| 8 | door open |
| 9 | door stage |
| 10 | mode |
| 11 | door policy |
| 12–13 | stable config version |
| 14–15 | candidate config version |
| 16–19 | применённый PWM fan 1..4 |
| 20–27 | RPM fan 1..4, четыре u16 |
| 28 | failed fan mask |

Сырые значения трёх концевиков и внутренний выход PID в компьютерную телеметрию не входят.

## Тестовые векторы

### RPM без специальной замены

`RPM=771` кодируется как `0x03 0x03`. Оба байта передаются без изменения, поскольку их позиции уже определены форматом.

`RPM=4000` → `0x0F 0xA0`; `RPM=6000` → `0x17 0x70`; `RPM=65535` → `0xFF 0xFF`.

### Температура

- `25.00 °C` → `0x19 0x00`;
- `25.50 °C` → `0x19 0x81`;
- `-0.25 °C` → `0xFF 0xC1`.

### Восстановление после неполного сообщения

Если после команды принято меньше ожидаемого числа полей и новых байтов нет 2 секунды, частичное сообщение отбрасывается. Следующий байт обрабатывается как новая команда.
